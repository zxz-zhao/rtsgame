# Godot 4 C# 3D RTS 全局架构审计报告

> **审计边界**：本报告基于当前已提供的里程碑、平台产物和测试标准进行架构级审计，并非对仓库源码、网络协议、Profiler 报告和线上遥测的逐文件验证。因此，涉及“已完成能力”的部分视为功能存在，不等同于已满足大规模联机、长周期稳定性和商业化发布标准。

## 一、总体结论

当前项目已经跨过“核心战斗演示”和“多端可打包”阶段，但尚未完成从单机/展示型 RTS 向商业化 RTS 的关键跃迁。最大结构性风险集中在：

- **P0：模拟层与表现层边界尚未被证明足够严格**。如果战斗逻辑直接依赖 Godot SceneTree、浮点物理、渲染帧和非确定性随机数，后续联机、回放、断线重连和状态校验都会反复返工。
- **P0：大兵团、战争迷雾、海陆空补给属于系统级闭环，目前里程碑主要证明了单元能力，尚未证明规模化系统能力。**
- **P0：Android 包体 1.45GB、API 35 ARM64 已发布，但包体、内存、热 throttling、GPU 帧时间和低端机稳定性仍缺少量化门禁。**
- **P1：自动化验证覆盖了编译、场景和短时录屏，但距离确定性回归、长时 soak、跨设备矩阵和网络故障注入仍有明显差距。**
- **P1：空间音频、物流、侦察信息和 UI 交互尚未形成统一的“战场信息反馈闭环”。**

建议先冻结高风险玩法扩展，优先建立 **Deterministic Simulation Core、规模化单位管线、性能预算和长周期验证体系**。

---

## 二、优先级定义

- **P0**：阻塞商业化、联机、核心可玩性或平台稳定性的基础问题；必须在继续扩大内容前解决。
- **P1**：不立即阻塞单机演示，但会显著限制规模、维护成本、用户体验或后续迭代速度。
- **P2**：增强项、长期技术债或内容质量问题，可在核心闭环稳定后处理。

---

# 1. 网络联机与确定性帧同步

## 现状判断

当前已证明战斗框架可以编译、单位可以运行，但尚未证明以下能力：统一 tick、输入指令协议、跨机器状态一致、断线重连、回放、校验和定位及作弊防护。PC 与 Android 可运行不代表模拟结果可复现。

## P0 风险：模拟层未完全确定性化

**根因与瓶颈**：

- Godot 物理、`float` 运算、节点遍历顺序、异步资源加载和线程调度可能产生平台差异。
- 战斗逻辑若分散在 `_Process`、`_PhysicsProcess`、动画回调和场景信号中，tick 边界不可控。
- 随机数、单位生成 ID、目标选择和碰撞排序若无固定规则，状态会逐步分叉。
- 仅同步位置或事件而不是同步玩家输入，无法可靠支持回放和状态修复。

**推荐架构**：

建立三层边界：

1. `SimulationCore`：纯 C#、固定 tick、无 Node/Rendering/Audio 依赖。
2. `PresentationLayer`：读取模拟快照，负责 Node3D、动画、特效、音频和插值。
3. `TransportLayer`：只传输带 tick、玩家 ID、序列号和校验信息的指令包。

采用固定 tick，例如 20 或 30 Hz；渲染帧只负责插值。所有排序使用稳定键，例如 `EntityId`；所有随机操作使用按比赛种子派生的确定性 PRNG；避免把平台相关物理结果写入核心状态。

**实施步骤**：

- 定义 `CommandFrame`、`SimulationTick`、`EntityState`、`StateHash` 和协议版本。
- 将移动、命中、伤害、资源、生产、视野和胜负判定迁移到纯模拟服务。
- 每 N 个 tick 生成分区哈希和全局哈希，支持差异定位。
- 实现双机同输入回放、暂停后继续、延迟输入、丢包和乱序测试。
- 增加快照同步与断线重连，不把客户端表现节点作为权威状态。

**验收标准**：

- 同一输入日志在 Windows、Android、无渲染 headless 环境运行 30 分钟，最终状态哈希一致。
- 1000 次随机对局无状态分叉；出现分叉时能定位到 tick、实体和字段。
- 回放逐帧复现；断线重连后状态与权威快照一致。

## P1：网络传输和服务端权威边界未完成

应明确 P2P、Dedicated Server 或 Relay 方案。商业化 RTS 推荐服务端权威、客户端输入驱动，并加入命令合法性校验、速率限制、重放保护和观战接口。需要定义延迟隐藏、输入等待窗口、慢客户端处理和比赛结束存档策略。

## P2：回放、观战和赛事工具缺失

在协议稳定后增加输入日志压缩、关键帧快照、倍速播放、战斗事件检索和观战延迟缓冲。这些能力应复用模拟核心，而不是另建逻辑。

# 2. 大兵团流场寻路与编队防挤压

## 现状判断

单个坦克、步兵、舰船和飞机能够运动，不等于具备大兵团寻路能力。当前最大未知项是单位数量、地图尺寸、障碍动态变化、跨地形通行和拥堵条件下的帧时间。

## P0 风险：缺少分层寻路和规模化拥堵模型

**根因**：若每个单位独立运行 A*、射线避障或物理碰撞，复杂度会随单位数和障碍数量快速增长，并且结果难以确定性同步。

**推荐架构**：

- 预计算或分块更新的多层导航网格。
- 集团级路径使用 Hierarchical A* 或区域图。
- 区域内使用 Flow Field：积分场、方向场、代价场分离。
- 单位使用编队槽位、局部偏移和轻量分离力，不使用高成本刚体互相推挤作为主要移动方案。
- 动态障碍采用占用网格和增量重算，按优先级分帧更新。
- 海陆空使用不同通行层和转换规则，避免用一套导航逻辑强行覆盖三类运动体。

**实施步骤**：

1. 先定义地图网格分辨率、区域边界、地形代价和动态占用协议。
2. 实现集团目标路径和缓存键：起点区域、目标区域、地形版本、威胁版本。
3. 为编队定义队形模板、槽位分配、队形缩放和障碍降级策略。
4. 将单位移动改为“目标速度 + 流场方向 + 槽位误差 + 分离修正”。
5. 为拥堵、窄口、桥梁、登陆点和撤退路线建立专项场景。

**验收标准**：

- 1000/3000/5000 单位压测时，路径计算不产生持续帧尖峰。
- 集团通过窄口后不出现永久卡死、周期抖动或队形无限膨胀。
- 同一 tick 下的路径和槽位结果跨平台一致。
- 动态障碍更新具备最大计算预算，超预算时有可控降级。

## P1：编队生命周期和指令语义需要统一

区分移动集团、攻击集团、运输编队、舰载机编队和撤退编队。明确合并、拆分、死亡、失联、重组和临时避障时的队形所有权，避免由 UI 或单个单位脚本隐式维护。

## P2：高级战术移动

后续加入分路推进、楔形突破、护航屏障、火力线保持、预留撤退通道和威胁场避让。这些功能必须建立在稳定的基础寻路数据之上。

# 3. 全动态战争迷雾与视距遮罩

## 现状判断

已有小地图和战术 UI，但尚未证明存在严格的数据层战争迷雾。需要区分“玩家曾经看见过的地图”“当前可见区域”“敌方单位最后已知位置”和“渲染层遮罩”。

## P0 风险：信息泄漏和视野判定不一致

**根因**：如果只在渲染层隐藏单位，敌方数据仍可能通过选择、碰撞、音效、网络包或 UI 泄漏。若视野直接依赖每帧物理射线，会造成性能和确定性问题。

**推荐架构**：

- `VisibilityState` 作为模拟数据：`Unknown`、`Explored`、`Visible`、`LastKnown`。
- 地图采用可配置栅格或分层遮罩，视野源以单位能力、地形高度和天气修正生成。
- 静态遮挡使用预烘焙高度/区域数据；动态遮挡使用有限预算的增量更新。
- 逻辑可见性与渲染遮罩分离：服务器决定可见数据，客户端决定如何显示。
- 敌方单位离开视野后保留“最后已知状态”，而不是继续同步实时位置。

**实施步骤**：

- 定义视野源组件：半径、锥角、夜视、水下、空中高度和探测类型。
- 实现按 tick 更新的可见性脏区和队列预算。
- 接入地形高度、建筑遮挡、烟雾、天气和侦察设备。
- 对小地图、主视图、目标选择、伤害数字和音效统一应用可见性权限。
- 记录视野事件，支持回放和作弊审计。

**验收标准**：

- 视野边界没有明显闪烁、穿透或一帧泄漏。
- 1000 个视野源下更新耗时有硬预算。
- 服务器向客户端发送的数据严格遵循可见性权限。
- 重放时视野结果与原始对局一致。

## P1：战术情报模型缺少分层

区分实时视野、雷达发现、声音线索、最后已知位置、伪装和诱饵。UI 不应把不同可信度的信息显示为同一种图标，否则会削弱战术决策价值。

## P2：高级侦察与反侦察

增加电子干扰、假目标、热源、潜艇声呐、空中预警和天气影响，但必须先稳定基础视野权限模型。

# 4. 海陆空攻防与补给调度闭环

## 现状判断

已具备坦克、步兵、防空、舰船、潜艇、航母和舰载机模型，但“模型存在”与“战略闭环完成”不同。当前关键缺口通常在任务状态、航程、弹药、燃料、返航、补给、维修和基地容量的统一状态机。

## P0 风险：舰载机/机场循环可能是表现逻辑而非领域状态机

推荐为飞机建立明确状态：`Ready -> Launching -> Transit -> Attack -> RTB -> Landing -> Refueling -> Rearming -> Repairing`。每个状态必须有进入条件、退出条件、失败原因、超时策略和可观测事件。

航母与机场应提供统一的 `AirOperationsProvider` 接口，飞机只依赖起降位、燃料、弹药、维修能力和安全航线，不直接访问具体场景节点。

**实施步骤**：

- 建立燃料、弹药、维修、挂载、起降位和补给队列的数据模型。
- 设计补给网络：基地、仓库、运输单位、路线、威胁和运输容量。
- 将补给中断、机场摧毁、航母移动、跑道占用和返航失败纳入模拟状态。
- 建立海陆空目标选择与威胁评估的统一接口。
- 为潜艇、舰船、飞机和地面单位分别配置运动与补给约束。

**验收标准**：

- 飞机在攻击、返航、低燃料、基地失效和起降位占用时不会进入死状态。
- 补给中断能被 UI、音频和日志明确反馈。
- 资源消耗、运输抵达和维修完成可回放、可校验。
- 海陆空系统在 30 分钟长局中无资源负数、重复补给或状态机卡死。

## P1：后勤网络和战役层脱节

需要把战术战斗中的燃料、弹药、维修与战略层产能、运输线、占领区域关联起来。建议用事件驱动记录 `SupplyRequested`、`SupplyDispatched`、`SupplyArrived`、`SupplyInterrupted` 和 `SupplyConsumed`。

## P2：高级后勤玩法

加入护航、封锁、空投、抢修、前线弹药车、港口吞吐量和天气导致的运输效率变化。前提是基础资源闭环可测试。

# 5. Android 触控与 Vulkan 性能

## P0：1.45GB 包体和资源内存风险

包体明显偏大，直接影响下载转化、安装空间、首启时间、补丁效率和低端设备稳定性。必须拆分高分辨率纹理、重复模型、未使用资源、调试符号和视频素材，并建立资源引用审计。

**性能架构**：

- 使用对象池、批处理、LOD、遮挡剔除、纹理压缩和实例化。
- 将模拟 tick、寻路、视野和渲染提交分开统计。
- 避免每帧 C# 分配、LINQ、闭包、字符串拼接和节点全树扫描。
- 明确移动端预算：目标帧率、主线程、渲染线程、GPU、内存、加载和热降频。
- 触控输入使用统一手势状态机，区分镜头平移、缩放、旋转、框选、点选和长按。

**实施步骤**：

1. 建立低、中、高设备矩阵和首屏、战斗、暂停、切场景采样流程。
2. 使用 Godot Profiler、Android GPU Inspector、Frame Pacing 和内存工具建立基线。
3. 按资源类型压缩和分包，控制纹理尺寸、材质数量和动画采样率。
4. 实施触控输入优先级、手势取消、边缘区域保护和误触回滚。
5. 对 500、1000、3000 单位分别执行稳定帧率与温升测试。

**验收标准**：

- 明确不同档位设备的目标 FPS、P95/P99 帧时间和内存上限。
- 连续 30 分钟战斗后无明显热降频导致的不可玩帧率。
- 触控手势在 UI 区域、地图边缘、双指缩放和框选冲突时行为一致。
- 无持续增长的 Managed/Native 内存泄漏。

## P1：输入与模拟命令可能耦合

触控层应生成设备无关的 RTS 命令，例如 `SelectRect`、`MoveGroup`、`AttackTarget`，而不是直接调用单位方法。这样可复用到鼠标、手柄、AI、回放和联机。

## P2：图形质量自适应

加入动态分辨率、阴影档位、粒子预算、后处理开关和战场密度降级，并将配置变化纳入性能回归测试。

# 6. 3D 空间音频与战斗反馈

## P1：音频尚未形成信息系统

空间音频不能只作为爆炸和引擎声效。RTS 需要通过声源位置、遮挡、距离、阵营、威胁等级和事件优先级传递无法持续注视的战场信息。

**推荐架构**：

- 模拟层发出无引擎依赖的战斗事件。
- 音频层根据事件、位置、可见性、听觉范围和优先级生成播放请求。
- 使用事件池和最大并发数，避免大规模战斗时音频爆发。
- 为空间音频定义距离衰减、遮挡、低通滤波、混音总线、阵营语音和移动端降级策略。

**实施步骤与验收**：

- 建立武器、命中、警报、返航、补给中断和基地受袭事件表。
- 验证音频与可见性、回放和暂停状态一致。
- 1000 个单位战斗中控制并发声源和 CPU 开销。
- 移动端低配模式下仍保留关键警报、方向性和语音优先级。

## P2：拟真增强

加入弹道方向反馈、远近爆炸层次、舰体结构声、潜艇声呐和环境混响。拟真效果不能以牺牲关键战术可读性为代价。

## 7. 自动化测试、长周期回归与 Rule 5

### 7.1 当前测试体系的边界

现有 `TC-01 ~ TC-05`、`AutoCombatScene` 和 20 秒以上录屏，能够覆盖：

- C# 工程是否可编译；
- 核心场景是否可以启动；
- 关键节点和资源是否存在；
- 基础战斗流程是否可运行；
- GPU 是否能够输出有效画面；
- 基础移动、动画和战斗表现是否正常。

但这些测试仍然主要属于“启动级”和“短时功能级”验证，尚不能证明：

- 长时间运行后没有内存、句柄或事件队列泄漏；
- 多平台模拟结果保持一致；
- 大规模单位下帧时间和 GC 可控；
- 网络异常不会破坏比赛状态；
- 飞机、补给、维修、视野和资源状态机不会进入死状态；
- Android 真机在热降频、后台切换和低内存场景下仍能稳定运行。

因此，当前测试体系的主要缺口不是测试数量不足，而是**缺少按系统风险组织的验证分层**。

---

### 7.2 P0：确定性、长周期和核心闭环没有形成硬门禁

#### 根因与风险

如果测试只检查最终画面或进程是否退出，就无法发现以下问题：

- 同一输入在 Windows 与 Android 上产生不同结果；
- 单位位置存在微小误差并在长局中逐渐放大；
- 随机数种子、实体 ID 或目标排序发生漂移；
- 飞机在返航、降落、补给或机场被摧毁后永久卡死；
- 资源、弹药、事件队列和对象池在长时间运行后持续增长；
- 局部帧率正常，但 P99 帧时间已经无法满足移动端体验。

#### 推荐测试分层

建立以下五级测试门禁：

1. **静态门禁**
   - 编译、警告、资源引用、场景契约、导出文件完整性；
   - 禁止测试场景依赖编辑器专用资源；
   - 检查脚本生命周期、空引用和平台条件编译。

2. **模拟层门禁**
   - 固定种子、固定输入、固定 tick；
   - Windows、Android 和 headless 环境运行同一输入日志；
   - 比较每个关键 tick 的全局哈希与分区哈希；
   - 失败时输出首个分叉 tick、实体 ID 和字段差异。

3. **压力与长周期门禁**
   - 500、1000、3000、5000 单位分级测试；
   - 30 分钟、1 小时和更长时间的 headless soak；
   - 记录帧时间、GC、内存、事件数量、实体数量和路径计算耗时；
   - 检查所有指标是否存在持续增长趋势。

4. **网络异常门禁**
   - 延迟、抖动、丢包、乱序、重复包和断线重连；
   - 慢客户端、服务器暂停、输入延迟和比赛结束存档；
   - 验证客户端不能通过非法命令修改资源或单位状态。

5. **真机与发布门禁**
   - Android 冷启动、热启动、后台恢复和低内存回收；
   - Vulkan 渲染、音频、触控、旋转和不同刷新率；
   - APK 安装、升级、卸载重装和存档兼容性；
   - 录屏不仅检查“有画面”，还检查黑屏、卡帧、崩溃和异常帧时间。

---

### 7.3 Android 真机测试与验收标准

#### P0：必须建立设备分层矩阵

至少建立以下三档设备：

- **低端设备**：低内存、入门级 GPU、60 Hz 屏幕；
- **主流设备**：项目目标用户的典型 Android 设备；
- **高端设备**：用于验证高画质、较大单位规模和高刷新率。

每档设备至少记录：

- Android 版本、SoC、GPU、内存容量；
- Vulkan 驱动版本；
- 屏幕分辨率和刷新率；
- 首次着色器编译时间；
- 冷启动和场景加载时间；
- 峰值内存和持续内存；
- CPU、GPU、渲染线程和主线程帧时间；
- 连续运行 30 分钟后的温度和降频状态。

#### P0：Android 功能验收

必须覆盖以下流程：

1. 首次安装并启动；
2. 首次资源导入或缓存生成；
3. 进入战斗场景；
4. 框选、点选、长按、双指缩放、双指旋转；
5. 地图边缘拖拽和镜头限位；
6. 小地图点击、拖拽和主视图同步；
7. 战斗、暂停、恢复和退出；
8. 切换后台后恢复；
9. 锁屏或系统中断后恢复；
10. 低内存情况下重新进入场景；
11. 存档、读取和版本升级兼容；
12. 网络断线、重连和比赛结束。

验收要求：

- 不得出现无法恢复的黑屏、输入锁死或镜头漂移；
- 触控手势之间不得发生持续误触和状态串扰；
- UI 触控区域必须避开系统手势区域；
- 断点恢复后模拟状态、镜头状态和 UI 状态必须一致；
- 所有错误必须能够记录设备型号、场景、tick、资源和堆栈信息。

#### P0：性能验收基线

建议建立明确预算，而不是仅以“主观流畅”作为标准：

- 目标帧率：根据设备档位设定 30 FPS 或 60 FPS；
- 关键战斗场景应记录平均帧时间、P95 和 P99；
- 主线程、渲染线程和 GPU 时间必须分别统计；
- 30 分钟运行后不得出现持续性内存增长；
- GC 不得在战斗高峰期造成周期性长暂停；
- 单位数量增加时，寻路、视野和渲染成本必须分别可观测；
- 设备出现热降频后必须进入可控画质或单位表现降级，而不是直接失去可玩性。

#### P1：自动化报告和趋势分析

每次构建自动生成：

- APK 版本、Git 提交号和配置档位；
- 设备信息；
- 启动时间、加载时间和场景切换时间；
- 峰值内存、GPU 时间、CPU 时间和帧时间分位数；
- 崩溃日志、ANR、渲染错误和资源加载失败；
- 与上一版本的性能差异。

性能回归应以趋势判断为主，不能只检查是否超过单一阈值。连续多个版本逐步恶化时，即使尚未超出硬阈值，也应建立技术债告警。

#### P2：长期兼容性覆盖

后续补充：

- 不同 Vulkan 驱动版本；
- 不同屏幕比例和刘海区域；
- 平板设备；
- 低刷新率与高刷新率设备；
- 外接手柄、鼠标和键盘；
- Android 系统语言、字体缩放和无障碍配置。

---

### 7.4 P1：回放、截图和视频测试的可信度不足

视频测试不能只验证“文件存在”和“画面非黑”。应增加：

- 固定输入日志和固定种子；
- 关键帧截图比对；
- UI 元素存在性检查；
- 画面黑帧、冻结帧和异常跳帧检测；
- 录屏时长与实际游戏 tick 对齐；
- 战斗事件日志与视频时间轴对齐；
- 不同图形质量档位的视觉回归。

对于允许少量视觉差异的场景，可采用区域化阈值比较；对于 UI、单位位置和关键战术图标，应使用更严格的像素或结构化检测。

---

### 7.5 P2：测试基础设施和诊断能力

建议建立统一的 `TestScenario` 描述格式，使每个测试场景明确声明：

- 初始地图；
- 玩家资源；
- 单位数量；
- 输入脚本；
- 随机种子；
- 预期事件；
- 预期状态哈希；
- 性能预算；
- 截图和视频验证点。

同时建立统一诊断输出：

- `simulation.log`；
- `network.log`；
- `visibility.log`；
- `logistics.log`；
- `performance.csv`；
- `state-hash.json`；
- `crash-report.json`。

这样可以把“测试失败”转换成可定位的系统问题，而不是仅得到一个失败退出码。

# 8. 架构师综合实施建议与近期里程碑路线图

## 8.1 总体实施原则

当前项目不宜继续无边界增加单位、武器和特效内容。接下来的工作重点应从“增加可展示功能”转向“建立可规模化、可联机、可验证的底层闭环”。

建议遵循四项原则：

1. **模拟优先**
   - 先保证固定 tick、确定性、状态快照和回放；
   - 表现层只消费模拟结果，不反向决定战斗结果。

2. **规模优先**
   - 以 1000 至 5000 单位作为架构约束；
   - 所有寻路、视野、音频和特效系统都必须有预算和降级策略。

3. **平台预算优先**
   - Android 不是 PC 的缩小版；
   - 包体、内存、热降频、触控和加载时间必须作为一等指标。

4. **测试先于扩展**
   - 新系统必须同时提供模拟测试、压力测试、异常路径测试和真机验证；
   - 未纳入测试的核心状态机不得进入商业化内容生产阶段。

---

## 8.2 P0 阶段：基础架构封锁与风险清零

### 目标

建立后续所有系统共同依赖的确定性模拟核心、性能基线和测试门禁。

### 主要任务

- 拆分 `SimulationCore`、`PresentationLayer` 和 `TransportLayer`；
- 统一固定 tick、实体 ID、随机数、排序和状态序列化；
- 建立输入命令协议和状态哈希；
- 完成双实例同输入回放；
- 建立单位数量分级压测；
- 建立 Android 低端、主流和高端设备基线；
- 完成 APK 资源引用审计和包体拆分；
- 设计飞机返航、补给、维修和机场状态机；
- 建立基础战争迷雾数据模型；
- 扩展测试门禁至确定性、长周期和异常路径。

### P0 验收条件

- 同一输入日志在不同平台得到一致状态哈希；
- 30 分钟以上战斗无明显内存和事件队列增长；
- 关键状态机不存在不可恢复死状态；
- Android 真机完成冷启动、战斗、后台恢复和低内存测试；
- 500、1000、3000 单位测试均有性能报告；
- 所有 P0 缺陷均有复现步骤、责任模块和回归测试。

---

## 8.3 P1 阶段：规模化战场系统闭环

### 目标

将单元级能力升级为集团级、战区级和多系统联动能力。

### 主要任务

- 实现分层导航、流场寻路和编队槽位；
- 引入动态障碍、窄口、桥梁、登陆点和撤退路径测试；
- 实现按 tick 更新的战争迷雾和最后已知位置；
- 统一小地图、主视图、目标选择和战术 UI 的可见性权限；
- 完成补给网络、运输队列、资源消耗和中断事件；
- 实现基础空间音频事件总线和并发控制；
- 增加网络延迟、丢包、断线重连和慢客户端验证；
- 完成服务端权威或明确的联机架构选型；
- 建立持续集成中的性能趋势报告。

### P1 验收条件

- 大规模单位在复杂地形下不会持续卡死或无限拥堵；
- 敌方信息严格遵循战争迷雾权限；
- 飞机、舰船、地面单位和补给系统能够完成完整生命周期；
- 网络异常后比赛可以恢复或明确结束，不出现双方状态永久分裂；
- 关键声音能够传递方向、距离和威胁等级；
- 主要 Android 设备完成连续长局验证。

---

## 8.4 P2 阶段：商业化体验和高级战术能力

### 目标

在核心稳定后提升内容深度、战术表达和平台适配质量。

### 主要任务

- 回放、观战、赛事和战斗统计；
- 高级侦察、反侦察、电子干扰和诱饵；
- 高级编队战术、护航、分路推进和威胁规避；
- 动态天气、环境声场和更精细的空间音频；
- Android 动态分辨率和图形质量自适应；
- 资源热更新、增量补丁和版本兼容；
- 更完整的运营数据、崩溃分析和性能遥测；
- 多语言、无障碍、手柄和键鼠兼容。

### P2 验收条件

- 新增玩法均复用统一模拟、事件、网络和测试接口；
- 回放与实时对局使用同一套确定性输入；
- 图形质量调整不会修改模拟结果；
- 版本升级不破坏存档、回放和协议兼容；
- 高级表现效果不会突破移动端性能预算。

---

## 8.5 建议的近期执行顺序

### 第一阶段：架构冻结

优先冻结以下接口：

- `ICommandSource`
- `ISimulationTick`
- `IStateSerializer`
- `IStateHasher`
- `IPathService`
- `IVisibilityService`
- `ILogisticsProvider`
- `IAudioEventSink`
- `IPerformanceProbe`

这些接口冻结后，单位、UI、网络和测试系统才能并行开发，避免继续通过场景节点直接互相调用。

### 第二阶段：建立可复现样本

建立三类固定测试局：

- 小规模：验证规则、伤害、资源和状态机；
- 中规模：验证寻路、视野、编队和补给；
- 大规模：验证性能、对象池、音频和渲染降级。

每个测试局都必须具备固定种子、固定输入、预期事件和状态哈希。

### 第三阶段：打通一条完整闭环

建议优先打通以下可验收闭环：

> 侦察发现目标 → 生成移动命令 → 集团寻路 → 进入战争迷雾判定 → 发起攻击 → 消耗弹药 → 请求补给 → 运输抵达 → 单位恢复战斗能力 → 回放并验证状态哈希。

这条闭环比继续增加单独单位模型更能证明项目已经具备 RTS 产品级基础。

### 第四阶段：再扩展内容和联机规模

只有在 P0 门禁稳定、长周期测试通过、Android 性能基线达标后，才适合继续扩展：

- 更多单位；
- 更复杂的武器；
- 高级天气；
- 复杂战役；
- 多人房间；
- 观战和赛事功能。

## 最终架构判断

当前项目的核心资产已经具备较强的战斗表现基础，但商业化 RTS 的主要风险已从“功能是否存在”转移到：

- 能否确定性运行；
- 能否支撑大规模单位；
- 能否在多端维持稳定帧时间；
- 能否避免战争迷雾和网络信息泄漏；
- 能否让海陆空与补给形成可验证闭环；
- 能否通过长周期和真机测试持续证明质量。

因此，近期最高优先级不是继续扩大内容规模，而是完成 **确定性模拟核心、规模化战场基础设施、Android 性能预算和长周期回归门禁**。这四项完成后，项目才具备进入稳定多人联机、长期运营和商业化内容生产阶段的技术条件。
