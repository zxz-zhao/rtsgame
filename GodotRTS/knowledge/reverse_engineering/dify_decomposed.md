 这类现象通常不是单一机制造成的，而是用户态、内核态和虚拟内存映射共同作用的结果。需要先区分两种情况：

1. `NtProtectVirtualMemory` 返回成功，但页属性实际上没有按预期改变。
2. 页属性改变了，但后续写入落到了别的物理页，或被保护组件立即恢复、丢弃。

常见实现大致有以下几类。

**1. 用户态 API 或 syscall stub 拦截**

保护器可能修改进程内的：

- `kernel32!VirtualProtect`
- `kernelbase!VirtualProtect`
- `ntdll!NtProtectVirtualMemory`
- 相关系统调用入口或返回路径

实现形式包括：

- inline detour
- 导入表或导出表重定向
- 修改 syscall stub
- 异常处理机制捕获特定执行路径
- 对调用参数、返回地址、目标区间进行检查

拦截器可以对映像范围、保护区、调用者地址进行判断。例如，对受保护模块中的地址强制保留原保护属性，或者调用真实内核服务后再恢复原状态。

这种情况下可以出现“调用返回成功但实际效果被覆盖”的现象，因为钩子可以伪造 `NTSTATUS`，或者在系统调用返回后重新设置页属性。仅检查返回值无法证明保护位最终状态。

需要注意的是，单纯修改 `ntdll` stub 并不能可靠阻止直接系统调用。成熟产品通常会组合使用内核驱动、完整性校验或其他检测机制，防止调用者简单复制一个 syscall stub。

**2. 内核驱动拦截虚拟内存操作**

保护器可以安装内核组件，在内核层观察或限制内存保护变化。可能的技术路径包括：

- 内核内存管理路径上的拦截或监控
- 对目标进程、目标地址区间和调用上下文进行策略判断
- 维护受保护区域清单
- 检查映像页的保护属性变化
- 检测可写、可执行、可读写之间的转换

驱动不一定需要直接替换公开 API。它可以在请求已经到达内核后，对结果进行修正，或者在操作完成后恢复保护属性。

这类机制可以解释：

- 用户态 `NtProtectVirtualMemory` stub 没有明显钩子，但行为仍被阻止
- 直接调用系统服务也没有效果
- 对普通匿名内存区域的保护修改正常，但对特定映像区间无效
- 返回值看起来正常，而随后查询到的属性被恢复

现代 Windows 版本对内核对象和内核代码完整性有较多约束，因此商业保护器通常更倾向于使用合法驱动、进程级监控、异常机制和映射策略组合，而不是依赖单一脆弱的内核补丁。

**3. 映像节和段对象层面的约束**

PE 映像通常不是简单的私有匿名内存，而是由节对象映射到进程地址空间。文件映像节和普通私有提交页在内存管理上的语义不同。

保护器可能利用以下特征：

- 映像节的原始节保护属性
- PE 节表中的 `IMAGE_SCN_MEM_*` 标志
- section object 的映射属性
- 映像页的共享属性
- 代码段和数据段是否属于 image-backed region
- 重新映射或重新建立映像视图

需要注意，Windows 的页保护并不是完全由 PE 节表永久决定的。正常程序可以通过 `VirtualProtect` 修改映像页的当前保护属性。因此，单靠 PE 节表通常不能阻止修改；它更适合作为保护器识别和恢复目标的依据。

一种常见策略是：把关键代码从原始映像视图复制到私有页或另一份映射中执行，然后持续维护“真实执行副本”和“表面映像副本”。此时修改原始映像页并不一定影响实际执行流。

**4. 写时复制和私有页重定向**

这是“保护属性看起来改变了，但修改没有影响真实代码”的重要原因。

映像页可能最初是共享的、文件支持的页面。当某个进程尝试写入时，内存管理器可能触发 copy-on-write，使该进程获得一个私有副本。保护器可以利用这一点：

- 让调用者写入私有副本
- 实际执行仍然跳转到另一份代码页
- 监控私有副本并在需要时丢弃或替换
- 对真实执行页保持只读或不可写
- 在异常处理路径中恢复原始内容

因此，下面几个地址概念可能并不等价：

- PE 映像中的虚拟地址
- 当前进程看到的虚拟页
- 文件映像支持的原始页
- 私有 COW 页
- 实际指令执行所在的代码副本

如果保护器把执行流转移到私有镜像、解密缓存或动态生成的代码区域，修改模块头或某个常规 `.text` 映射自然不会影响执行结果。

**5. 重新映射和镜像替身**

另一类实现是维护多个视图或多个副本：

- 原始映像视图用于通过完整性检查
- 解密后的私有视图用于执行
- 诱饵视图用于干扰分析
- 修改后的页被重新映射到不参与执行的区域
- 关键函数通过跳板、间接分发器或解释器执行

这种方案可以让外部观察到的映像布局与实际执行布局不一致。保护器还可以在检测到某页被改写后：

- 重新映射原始页
- 从资源或加密存储恢复页面
- 将执行流切换到备用副本
- 终止或降级部分功能
- 触发延迟校验，而不是立即响应

这类设计不一定依赖 `VirtualProtect` 拦截，因此可能表现为 API 调用正常、页属性也发生变化，但程序行为仍然不受写入影响。

**6. 页故障、Guard Page 和异常驱动控制流**

保护器可以把关键区域设置为：

- `PAGE_GUARD`
- 只读或不可执行
- 特定访问模式下才临时开放
- 访问后立即恢复

再通过 VEH、SEH 或内核异常路径处理页故障。典型行为是：

1. 代码页默认处于受限状态。
2. 首次执行或写入触发异常。
3. 异常处理器确认访问者、线程、调用链和目标地址。
4. 临时解密或改变页属性。
5. 单步、执行或写入完成后恢复原状态。

如果写入请求没有满足保护器预期的上下文，异常处理器可以让写入看似完成，但之后恢复原始页面。也可能通过异常处理逻辑将执行流引向另一个副本。

这类机制通常伴随线程、返回地址、寄存器状态和调用栈检查。

**7. 虚拟化或监控层面的页权限控制**

更强的保护方案可能使用虚拟化技术或安全产品提供的监控能力，在二级地址转换层面控制页面：

- EPT/NPT 权限限制
- EPT execute-only 或读写执行分离
- EPT violation 后由监控组件处理
- 对特定进程或地址范围进行影子页映射
- 在客户机页表权限允许时，二级页表仍拒绝访问

这种情况下，进程内部查询到的页表和 `VirtualQuery` 结果可能显示为可写，但二级地址转换层仍然可以阻止、重定向或模拟该访问。

如果监控层选择模拟成功返回，就会出现“API 和页表观察结果正常，但实际写入无效”的表象。此类方案一般还会监控调试器、线程创建、异常和代码完整性事件。

**8. 持续完整性校验和快速恢复**

有些保护器并不真正阻止写入，而是允许短暂修改，然后通过以下方式恢复：

- 定时线程扫描
- 关键基本块进入和退出时校验
- 控制流转移点校验
- 线程上下文切换时校验
- 异常或系统调用返回路径校验
- 校验和、哈希、加密摘要或指令级白名单

从调用者角度看，写入可能已经发生，但在下一次执行前被恢复，所以容易被误判为“写入不生效”。

这类保护通常还会把校验对象分成多个粒度：

- PE 头和节表
- 导入表、重定位表
- 关键函数入口
- 控制流分发器
- 解密后的临时代码页
- 跳板和返回地址

**9. 对 API 结果和观测接口进行欺骗**

除了拦截修改接口，还可以影响观测结果：

- 对 `VirtualQuery` 返回值进行包装
- 伪造保护属性
- 对目标地址做别名映射
- 让读取接口返回原始内容，而执行使用另一份内容
- 在不同线程或不同调用上下文下返回不同视图
- 延迟真正的状态更新

所以应当把以下结果分开验证：

- API 返回值
- `VirtualQuery` 的逻辑属性
- 实际写入后的字节
- 实际执行的字节
- 页是否仍由 image section 支持
- 页是否发生了 COW
- 执行地址是否仍位于原映像
- 写入后是否被恢复

**10. 多机制组合是最常见的**

商业保护器通常不会只依赖一种技术。一个较现实的组合可能是：

1. 用户态包装 `VirtualProtect` 和 `NtProtectVirtualMemory`。
2. 对 `ntdll`、关键入口和保护目录做完整性检查。
3. 使用驱动监控进程和地址范围。
4. 将关键代码复制到私有解密区。
5. 对原始映像和执行副本分别做完整性校验。
6. 对可疑写入触发异常、恢复或切换执行副本。
7. 对 syscall、线程、调试器和异常行为进行关联检测。

因此，仅看到 `ntdll!NtProtectVirtualMemory` 被 inline hook，不能说明“阻止机制就是这个 hook”。hook 可能只是早期筛选层，真正决定结果的可能是私有代码副本、写时复制、驱动策略或后续完整性恢复。

从诊断角度，可以把现象归类为：

| 现象 | 更可能的机制 |
|---|---|
| 返回失败，状态码明确拒绝 | 用户态或内核态策略拦截 |
| 返回成功，保护属性立即恢复 | hook、驱动或异步恢复 |
| 属性变为可写，但执行行为不变 | 执行副本、跳转重定向、COW |
| 写入后立即读回原值 | 写入拦截、别名映射、写入后恢复 |
| 读回已修改值，但执行仍使用旧指令 | 实际执行地址不在该页，或 CPU/监控层使用另一副本 |
| 普通匿名页可修改，映像页不可修改 | image-backed 区域策略或保护器地址白名单 |
| 只有特定线程或调用栈有效 | 上下文校验、异常驱动或线程策略 |
| 直接系统调用也无效 | 内核驱动、虚拟化层或执行副本 |

关键结论是：`STATUS_SUCCESS` 只表示某一层接受了请求，不保证最终页属性、最终物理页或实际执行副本发生了对应变化。要理解具体实现，需要同时观察虚拟地址类型、映射来源、COW 状态、实际执行地址、异常路径以及是否存在内核或虚拟化监控；单独分析 `VirtualProtect` 或 `NtProtectVirtualMemory` 往往不足以解释现象。

这种情况下，运行内存 dump 本质上只是某一时刻的**部分状态快照**，而不是完整的可执行映像。PA（protect-on-demand）把“代码是否存在于明文内存中”变成了一个随执行路径变化的运行时条件。

**为什么单纯 dump 不够**

1. **大部分页根本尚未解密**  
   dump 得到的是密文页，而不是可直接执行的 VM 字节码。由于解密按 handler 或按页触发，未覆盖到的路径不会进入明文状态。

2. **已解密内容通常只是瞬时状态**  
   某些保护器会在 handler 返回、切换上下文或发生异常时重新加密；即使当前样本观察到“多次采样内容相同”，也只能说明这些页在采样窗口内没有重加密，不能说明其他未执行页已经可获得。

3. **明文代码和运行时状态不等价于原始映像**  
   可运行的 VM 通常还依赖：
   - 字节码区段布局和边界；
   - handler 表、分发表、跳转表；
   - 虚拟寄存器和 VM 栈；
   - 解密密钥或密钥派生状态；
   - 页状态位、访问权限和异常处理逻辑；
   - 运行时重定位、外部 API 映射和上下文初始化。

   这些内容可能位于寄存器、TLS、堆对象、栈帧或保护器私有元数据中，未必随某一份内存页快照形成完整闭包。

4. **dump 只覆盖一条执行路径**  
   即使把当前时刻所有明文页保存下来，也通常只得到当前输入、当前环境和当前控制流触发过的 handler。条件分支、异常路径、平台相关路径、延迟初始化路径都可能仍是密文。

5. **页面内容相同不代表页面已经完整暴露**  
   “非重加密”这个观察很重要：它排除了某些周期性随机化机制，但不能解决覆盖率问题。一个未访问页可以在整个观察期间始终保持同一份密文；其稳定性反而说明它一直没有进入解密状态。

6. **页粒度和 handler 粒度可能不一致**  
   一个页可能包含多个 handler，其中只有部分字节被解密；或者解密结果依赖前置状态。于是“这个页已变成低熵”也不等于该页内所有逻辑都已经可用。

因此，dump 更准确地说是：

> 当前执行轨迹下，已经驻留或曾经驻留过的明文、密文区、运行时元数据和 VM 状态的混合快照。

它不是完整的、可脱离保护器独立运行的映像。

**学术界和工业界的主流处理思路**

通常是组合使用，而不是依赖一次性 dump。

### 1. 动态覆盖与增量采集

让目标在受控环境中运行，记录每次：

- 解密触发；
- 页面权限变化；
- VM 入口和退出；
- handler 分派；
- 虚拟指令或虚拟 PC 变化；
- 异常和间接跳转。

在页面首次转为明文时立即保存，并记录其对应的虚拟地址、状态和来源。最终得到的是一个按执行轨迹累积的“明文页面集合”，而不是一次快照。

常见的实现基础包括调试器断点、页保护异常、动态二进制插桩、硬件执行追踪和虚拟机监控器级事件记录。

### 2. 监控解密器和 VM dispatcher

PA 保护的关键位置通常比较集中：

- 页解密例程；
- handler 查找和分派逻辑；
- VM 字节码取指逻辑；
- 虚拟寄存器更新位置；
- VM 退出到原生代码的位置。

工业工具通常优先识别这些运行时边界，围绕它们建立日志和状态采集，而不是试图直接从密文区静态恢复全部代码。

这类方法的价值在于：即使 handler 本身高度混淆，只要能识别“何时取出一个虚拟操作、何时完成一次分派”，就可以逐步建立 VM 的执行模型。

### 3. 路径导向的解包和覆盖率提升

因为 PA 的主要难点是路径覆盖，实际分析一般会使用多组输入和环境：

- 不同命令行、文件、网络和配置；
- 不同异常条件；
- 不同平台或系统版本；
- 模糊测试生成的输入；
- 记录后重放的执行轨迹。

对于受保护程序，单次正常运行通常只能揭示很小的路径子集。多次运行的目标不是简单增加运行时间，而是覆盖更多 VM 基本块、handler 和条件分支。

### 4. 动态执行轨迹到 IR 的提升

研究和工业逆向工具常把观察到的虚拟执行转换为中间表示，例如：

- 虚拟寄存器读写；
- VM 栈操作；
- 内存访问；
- 条件分支；
- 算术和逻辑操作；
- 原生调用边界。

随后在 IR 层做常量传播、死代码消除、控制流恢复和语义归并。这样得到的结果通常不是原始源码，也未必是原始机器码，而是一个**语义等价或近似等价的中间程序**。

这也是处理强虚拟化时更现实的方向：恢复行为和控制流语义，而不是要求恢复保护器发布前的原始布局。

### 5. VM 模型恢复与解释器化分析

如果能识别：

- 虚拟指令编码；
- 虚拟寄存器集合；
- 虚拟栈规则；
- handler 调度方式；
- 条件标志和内存模型；

就可以建立一个外部 VM 模型，对已记录的字节码和状态进行离线解释。之后可以把每个虚拟指令映射到统一 IR，再逐步合并 handler 语义。

这类方法对“handler 代码被拆散、混淆严重，但 VM 结构稳定”的保护尤其有效。

### 6. 符号执行、合并路径和约束求解

对于难以自然触发的分支，会使用符号执行或混合执行推导输入约束，以覆盖特定路径。通常不会对整个程序直接做全量符号执行，因为状态空间很快爆炸，而是针对：

- 未覆盖的 VM 分支；
- handler 中的关键条件；
- 解密触发条件；
- 环境检查；
- 分发索引计算。

工程上更常见的是“动态执行负责缩小范围，符号方法负责补关键路径”。

### 7. 检查点、回放和时间序列采集

PA 分析往往需要保存多个时刻的状态：

- 解密前；
- 解密后；
- handler 执行中；
- handler 返回后；
- 页面重新加密或权限恢复后。

通过检查点和确定性回放，可以比较同一页面在不同阶段的状态，区分：

- 固定密文；
- 永久明文；
- 短暂明文；
- 依赖运行时密钥的明文；
- 仅在特定路径生成的代码。

这比单个 dump 更能还原页面生命周期。

### 8. 原生代码和 VM 代码的边界分析

实际产品往往不是全部逻辑都虚拟化。常见结构是：

- 原生加载器；
- VM dispatcher；
- 一段或多段虚拟化区域；
- 原生 API 桥接；
- 保护检查和退出逻辑。

因此工业流程通常先恢复这些边界，再分别处理原生部分和虚拟部分。把整个进程当成一个连续的“加密代码区”会增加分析难度，也容易误判数据页、跳板页和缓存页。

**关键限制**

这类方法也没有保证能恢复“完整原始映像”：

- 未触发的路径仍然可能缺失；
- 输入相关或环境相关的代码可能不可达；
- 密钥可能由外部状态派生；
- 保护器可能故意生成一次性或上下文相关的 handler；
- 完整恢复可能在计算上接近路径覆盖、程序等价性或通用解混淆问题。

所以实际目标通常分成三档：

1. **可重复执行**：获得某条或某组路径的可回放表示；
2. **语义恢复**：恢复足够准确的 VM 指令、控制流和外部行为；
3. **映像重构**：尽量生成独立可运行的替代实现。

对 PA 型虚拟化，第二档通常比第三档更现实。简而言之，主流路线是：

> 运行时定位解密和分派边界，持续收集明文与 VM 状态，通过多路径覆盖建立虚拟执行轨迹，再将轨迹提升为 IR 或外部 VM 模型。

而不是期待一次内存 dump 自动产出完整、独立、可运行的保护前映像。

这种 PA（protect-on-demand）布局下，单次运行内存 dump 得到的通常只是“某一时刻的运行时切片”，不是完整的、可独立启动的程序映像。

**为什么 dump 不够**

1. **大多数 handler 从未被解密**
   
   保护器把 VM 字节码或 handler 按页保存为密文，只有执行路径即将进入某个 handler 时才临时解密。运行 25 秒后仍有 89%/99% 页面保持高熵，说明这些页面可能根本没有进入过解密状态。它们在 dump 中仍然是密文，无法直接反汇编或重新执行。

2. **解密窗口可能是瞬时的**
   
   常见流程类似：

   ```text
   密文页
       -> 解密
       -> 执行少量指令
       -> 清零/重新加密/切换保护
   ```

   即使保护器没有重新加密，也不代表所有页面曾经同时以明文存在过。普通 dump 只捕获采样时刻，容易错过正在使用的明文页。

3. **采样会丢失时间维度**
   
   单次 dump 记录的是空间状态，不记录页面在此前不同时间点曾经出现过的内容。若不同 handler 在不同输入、不同控制流下按需解密，那么完整的明文集合是多个时间片的并集，而不是某一个时刻的内存快照。

4. **“未重加密”不等于“已解密”**
   
   你观察到多次采样密文内容完全相同，通常只能说明：

   - 密文是稳定的 backing store；
   - 保护器没有对这些未触碰页面进行随机重加密；
   - 页面可能始终没有进入过解密路径。

   这反而支持“惰性解密”模型，而不是说明 dump 可以恢复它们。

5. **密钥和上下文可能不在页面中**
   
   解密过程可能依赖：

   - 寄存器中的临时值；
   - 每个 VM、线程或 handler 的上下文；
   - 动态生成的 key/nonce；
   - 页号、字节码偏移、执行计数器；
   - 运行时状态和控制流历史。

   即使拿到了某个时刻的内存内容，也可能缺少重新解密所需的完整上下文。

6. **虚拟化代码不是普通代码布局**
   
   可执行语义往往分散在多个部分：

   - VM dispatcher；
   - handler 表或 handler 地址解析逻辑；
   - VM 字节码；
   - 虚拟寄存器和栈；
   - 动态解密器；
   - 输入相关的分支状态；
   - 运行时解析出的 API、导入和重定位信息。

   因此，“把 dump 中的页拼回去”通常不能自动恢复一个可以脱离保护器启动的 PE/ELF。最多得到一个包含当前 dispatcher、当前明文 handler 和部分运行时数据的快照。

7. **当前路径不代表完整程序**
   
   如果某些 VM opcode、异常路径、平台分支或错误处理分支尚未执行，它们对应的 handler 就不会被解密。覆盖率不足时，恢复结果天然是不完整的。

所以，PA 型虚拟化的关键障碍不是“dump 工具抓不到内存”，而是**明文代码的存在具有时间和路径条件**。完整明文集合需要跨多个执行阶段、多个输入和多个控制流状态进行收集。

**学术界的主流思路**

学术工作通常把问题建模为“执行驱动的语义恢复”，而不是静态 dump。

1. **动态二进制插桩和执行跟踪**

   在 handler 进入、解密完成、跳转离开等边界记录：

   - 当前页和偏移；
   - 解密前后内容；
   - 实际执行的基本块；
   - VM opcode；
   - 虚拟寄存器变化；
   - handler 间的转移关系。

   常用技术路线包括 DBI、硬件断点、单步跟踪、异常/页权限事件，以及基于 PT 的控制流记录。重点是把采集触发点放在“明文已经可执行、但尚未被清理”的窗口内。

2. **事件驱动的页面采集**

   不等待定时 dump，而是在以下事件发生时采样：

   - 页权限从不可执行变为可执行；
   - 解密函数返回；
   - dispatcher 即将调用 handler；
   - 目标页发生写入；
   - 执行流首次进入某个 handler。

   这类方法得到的是一组按时间排列的页面版本，而不是一个静态快照。之后再根据地址、版本和执行时间重建候选明文集合。

3. **覆盖率引导的输入生成**

   通过 fuzzing、符号执行或 concolic execution 让程序进入新的 VM opcode 和 handler。目标通常不是覆盖普通 native 基本块，而是覆盖：

   - 未执行的 VM 指令；
   - 未触发的 handler；
   - 异常和边界路径；
   - 输入相关的虚拟分支。

   对 PA 保护而言，覆盖率直接决定能够观察到多少明文。

4. **动态语义归一化**

   研究者通常不追求立刻恢复原始 native 指令，而是先把每个 handler 表达成统一的中间表示，例如：

   ```text
   输入虚拟寄存器
       -> handler 语义
       -> 输出虚拟寄存器
       -> 下一条 VM 字节码位置
   ```

   然后在 IR 层进行去混淆、等价 handler 合并、常量传播和控制流恢复。这比直接把碎片化 handler 拼成原始函数更稳定。

5. **动态污点和数据流分析**

   对 VM 字节码、虚拟寄存器、真实输入和 native 内存进行污点跟踪，区分：

   - 控制流相关状态；
   - 算术/逻辑数据；
   - 地址和内存访问；
   - 解密 key 或上下文；
   - 仅用于反调试的干扰状态。

   目的通常是恢复真实数据流和语义，而不是简单收集所有执行过的字节。

6. **受控仿真或系统级仿真**

   把目标放进可控的仿真环境，在内存访问、页权限变化、异常和间接跳转处获得更细粒度的观测。仿真适合研究复杂的自修改和保护机制，但速度和环境兼容性通常是代价。

**工业界的主流做法**

工业工具链一般采用“动态解包/动态提取 + 语义分析”的组合，常见分层如下：

1. **先恢复运行时边界**

   识别 dispatcher、解密器、handler 调度点和 VM 上下文结构。先回答“什么时候页变成可执行明文”和“明文何时失效”，而不是直接扫描整个进程寻找低熵页。

2. **在解密完成点采集**

   通过调试器、DBI、虚拟机监控器或页权限监控，在明文窗口采集页面、基本块和寄存器状态。对于短暂明文，通常需要事件断点或执行钩子，而不是定时全进程 dump。

3. **构造多次运行的内容库**

   每次运行记录：

   ```text
   页面地址 + 页面版本 + 解密上下文 + 触发输入 + 执行范围
   ```

   然后进行去重、版本合并和冲突检查。单次快照解决不了的问题，靠多次路径执行积累覆盖。

4. **动态恢复导入、重定位和异常信息**

   对最终想生成的可执行文件，还需要处理运行时解析的 API、间接调用、异常表、TLS、线程局部状态和初始化顺序。仅仅收集代码页通常无法生成可正常启动的文件。

5. **必要时只生成“分析表示”**

   对高度虚拟化目标，工业实践往往不强求恢复原始 PE/ELF。更实用的结果可能是：

   - VM opcode 到语义 IR 的映射；
   - handler CFG；
   - 可执行路径 trace；
   - 输入/输出行为模型；
   - 某个函数的去虚拟化版本。

   这类表示足以完成漏洞分析、恶意代码研判、兼容性审计或行为提取，且比重建完整原始映像成本低很多。

**实际结论**

在你描述的观测下，更合理的判断是：

- 那些高熵且跨采样不变的页面，大概率是尚未触碰的稳定密文存储；
- 单次 dump 只能恢复当前时刻已经常驻的明文和运行时状态；
- 要获得完整可执行覆盖，必须沿不同路径重复触发解密，并在解密/执行边界采集；
- 最终结果通常先是“按时间组织的明文片段和 VM 语义”，之后才考虑是否能重建独立映像。

换句话说，PA 型虚拟化的核心对象不是一个静态文件，而是：

```text
密文 backing store
+ 按需解密事件
+ 执行路径
+ VM 状态
+ 多次运行得到的覆盖集合
```

缺少其中的时间维度和执行上下文，单纯扩大 dump 范围也不能把未曾解密的 handler 变成可运行代码。

## 公开工具和方法的现实情况

### NoVmp / VTIL 系

这类方案的核心价值仍然是：

1. 找到虚拟机入口和 dispatcher；
2. 提取 handler；
3. 将 handler 翻译成中间表示；
4. 对虚拟寄存器、虚拟栈和 VM 状态做数据流分析；
5. 合并或优化虚拟指令；
6. 输出 VTIL 或进一步生成原生代码。

它们的难点不在于“支持 x86 指令集”，而在于：

- VMProtect 版本和编译选项会改变 handler 结构；
- 同一版本不同样本的 opcode、密钥、dispatcher 组织可能不同；
- 32 位版本大量依赖真实栈和隐式寄存器状态；
- EFLAGS、段寄存器、异常、未对齐访问和内存别名会影响语义；
- handler 往往包含 MBA、条件分支、动态解码和反分析逻辑。

因此，即使某个框架声明“支持 VMProtect 3.x”，也不能简单推断它对 3.8x 的 32 位样本可直接工作。

### MogVMP 一类项目

这类项目通常比通用 VTIL pipeline 更偏向针对 VMProtect 的模式识别和自动化处理。对于 3.0–3.5 可能有较好的实用性，但到 3.8x 以后，真正的限制通常不是“版本号不匹配”本身，而是：

- handler 模板变化；
- bytecode 解码和虚拟指令提取流程变化；
- dispatcher/handler 的控制流混淆变化；
- 保护器生成的随机化和样本间差异；
- x86 与 x64 目标的状态模型不同。

如果项目没有明确列出 **x86、3.8x、完整样本恢复、异常路径和可执行输出** 的测试结果，应把“支持”理解成“可能能识别部分结构”，而不是稳定的自动反虚拟化。

### 2024–2025 的新公开方向

这两年公开研究更多集中在通用方向，而不是一个专门针对 VMProtect 3.8x x86 的成熟产品：

- 基于 lifting/IR 的 handler 语义归约；
- 使用 SMT/SymCC/angr/Miasm/LLVM IR 做局部语义等价；
- 基于 trace 的虚拟指令识别；
- 污点分析定位虚拟栈、虚拟寄存器和 bytecode；
- 通过动态执行收集 handler 样本，再做模板归纳；
- 用神经模型或 pattern mining 辅助识别 VM handler，但通常不能替代语义验证；
- 针对控制流平坦化和虚拟机混淆的通用反混淆研究。

这些成果对实现一个内部工具有参考价值，但目前仍没有看到一个公开、稳定、广泛复现的方案，可以宣称：

> 输入任意 VMProtect 3.8x x86 样本，自动恢复高质量原生函数。

更准确的结论是：**公开生态中存在可组合的组件和方法，但缺少针对该组合的成熟端到端工具。**

## 符号执行加污点分析的工程量

如果目标只是恢复一小段简单 handler，工程量不算特别大；如果目标是对真实函数做稳定的语义恢复，规模会明显上升。

### 1. 研究原型

目标：

- 定位 VM 入口；
- 标记虚拟栈、虚拟寄存器、VM context；
- 对单个 handler 做污点传播；
- 使用符号执行得到输入输出关系；
- 输出类似：

```text
vreg_3 = vreg_1 xor vreg_2
vreg_4 = load32(vmem + offset)
branch condition = ...
```

大致规模：

- 1 名熟悉 x86、逆向和 SMT 的工程师；
- 1–3 个月；
- 约 5,000–15,000 行有效代码，取决于复用的 lifter 和 IR；
- 只能覆盖少数 handler、有限路径和有限数据类型。

这个阶段更像验证可行性，不能称为完整 devirtualizer。

### 2. 可用的样本级工具

目标：

- 自动识别 dispatcher；
- 自动提取 handler；
- 处理 handler 内部常见混淆；
- 建立完整的 VM 状态模型；
- 对 handler 做缓存和归一化；
- 把多个虚拟指令合并成基本块；
- 输出 CFG 或中间表示；
- 对结果进行动态回放校验。

大致规模：

- 2–4 名工程师；
- 6–12 个月；
- 约 20,000–60,000 行代码；
- 需要大量样本驱动调试；
- 仍然通常只覆盖某一批构建配置或某一类保护选项。

这是比较现实的“内部生产工具”规模。

### 3. 接近通用的 x86 VMProtect 3.8x 反虚拟化框架

目标：

- 覆盖不同 3.8x 构建；
- 支持多种 handler 变体；
- 正确处理 EFLAGS、内存别名、调用约定；
- 支持 native/virtual 混合代码；
- 支持异常和非线性控制流；
- 输出可重定位、可重新链接或可执行的原生代码；
- 通过动态和静态等价验证。

大致规模：

- 3–6 名有逆向、编译器、符号执行经验的工程师；
- 12–24 个月；
- 约 50,000–150,000 行工程代码，通常还包括大量规则、样本数据库和测试 harness；
- 维护成本高于首次开发成本。

如果还要覆盖浮点、SSE、SEH、TLS、间接调用、异常边界和复杂的混合执行路径，工作量可能继续增加。

## 为什么“符号执行 + 污点分析”不能直接解决问题

这个组合适合解决的是：

- 哪些输入影响 handler 输出；
- 哪些内存位置代表虚拟栈或虚拟寄存器；
- 哪些条件决定 handler 的分支；
- 某个 handler 在局部路径上的等价语义。

但它不能自动解决以下问题：

### 路径爆炸

一个 handler 可能有多层条件分支，且分支条件包含：

- 位运算；
- MBA；
- 加密或解码；
- 依赖内存的查表；
- 依赖外部状态的条件。

需要路径合并、约束简化、切片和超时策略，否则 SMT 求解成本很快失控。

### x86 隐式状态

x86 反虚拟化中容易被低估的是 EFLAGS：

- `ADC/SBB` 依赖 CF；
- `SETcc/Jcc` 依赖多个 flag；
- `LAHF/SAHF` 会搬运部分 flag；
- `INC/DEC` 不修改 CF；
- `MUL/IMUL` 对 CF/OF 有特殊定义；
- 未定义 flag 不能被简单当成任意值或固定值。

如果 IR 没有精确建模 flags，恢复出来的语义可能在正常路径上看似正确，但边界输入会失败。

### 内存别名

虚拟栈、VM context、原生栈、输入缓冲区和临时内存可能互相重叠。简单的“每个地址一个符号变量”模型会导致：

- 不必要的约束膨胀；
- 错误地合并不同内存对象；
- 无法判断 load/store 是否别名；
- 生成的表达式过度保守。

### 语义归一化

符号执行得到的表达式不等于可读语义。例如：

```text
((x ^ k1) + k2) ^ ((x ^ k1) >> 13)
```

可能需要：

- 常量折叠；
- MBA 归约；
- bit-vector rewrite；
- 识别 rotate、mask、sign extension；
- 识别栈操作、比较、条件移动；
- 将等价表达式映射回虚拟 ISA。

这里通常需要大量规则和测试，而不是单纯增加 SMT 能力。

## 推荐的技术路线

如果目标是做研究或内部分析工具，比较现实的架构是：

1. **动态定位**
   - 记录 VM 入口、dispatcher、handler 执行轨迹；
   - 收集寄存器、栈、内存访问和分支信息。

2. **污点和状态识别**
   - 将 bytecode、VM context、虚拟栈、native stack 分开标记；
   - 识别 handler 对 VM 状态的读写集合；
   - 对每个 handler 建立输入输出摘要。

3. **x86 lifting**
   - 统一 lift 到 bit-vector IR；
   - 显式建模寄存器部分写入、EFLAGS、内存和调用约定；
   - 尽量复用成熟 lifter，而不是自己重新实现完整 x86 语义。

4. **局部符号执行**
   - 以单个 handler 或短 handler 序列为边界；
   - 采用 bounded execution；
   - 做路径合并、表达式切片和超时降级；
   - 不要一开始就对整个虚拟函数做全路径符号执行。

5. **语义匹配**
   - 将 handler 的状态转换归一化；
   - 识别 push/pop、load/store、算术、比较、跳转、调用等操作；
   - 建立样本内的虚拟 opcode 到语义操作映射。

6. **动态等价验证**
   - 对原始 VM 执行和恢复后的 IR/native 执行做 differential testing；
   - 使用随机输入、边界输入和路径导向输入；
   - 对寄存器、flags、内存副作用和返回值逐项比较。

7. **最后才做代码生成**
   - 先输出稳定的 IR、CFG 和语义摘要；
   - 代码生成应该是后续阶段；
   - 否则很容易把错误的状态模型固化成错误机器码。

## 结论

针对 **32 位 x86 + VMProtect 3.8x**：

- 目前不宜假设存在一个公开、成熟、通用的一键工具；
- 更现实的做法是组合现有 lifter、IR、动态插桩、污点分析和 SMT 组件；
- 仅恢复局部 handler：大约是数周到数月；
- 做成可分析一批真实样本的工具：大约 6–12 个月、2–4 人；
- 做成接近通用的反虚拟化框架：通常需要 1–2 年以上，并且需要持续维护；
- 符号执行和污点分析适合作为语义恢复的组成部分，但不能替代 dispatcher 识别、状态建模、表达式归约和动态验证。

评估某个新项目是否真正支持该组合时，建议重点看它是否公开展示了 **32 位样本、3.8x 构建、跨样本测试、EFLAGS 处理、异常/间接调用、恢复结果和动态等价验证**。只写“支持 VMProtect 3.x”或“支持 x86/x64”本身，证据强度是不够的。

**通常相对适合做受控插桩的目标**

前提是目标属于你自己维护的代码，并且保护器明确排除了它们：

- 业务层、边缘层、纯计算函数；

- 调用约定和参数布局；
- 返回值类型、结构体返回规则和寄存器使用；
- 栈对齐、异常展开信息和尾调用行为；
- 线程局部状态、锁顺序和重入语义；
- 原函数的副作用、错误码和所有权约定。

- 完整性校验、反篡改、许可证、签名和密钥处理函数；
- 进程启动、CRT 初始化、TLS 回调、模块加载和卸载路径；
- 异常分发、崩溃处理、栈展开、线程创建和同步原语；
- 内存分配器、堆管理、低层系统调用封装；
- 控制流保护、间接调用分发、跳板和 thunk；
- 编译器生成的安全检查、栈 cookie 相关代码；
- 被多个模块共享的 ABI 边界函数；
- 频繁执行且有严格时序或递归调用约束的内部函数；
- 位于只读代码页、签名区域或已登记代码范围中的函数。

改返回值尤其危险。返回值可能被用于：

- 后续长度计算、索引或内存复制；
- 引用计数、资源句柄和对象生命周期；
- 状态机转换；
- 加密验证和许可证状态；
- 线程同步或错误恢复路径。

所以“函数本身没崩”并不代表修改是安全的，错误值可能稍后以堆损坏、非法间接调用或保护器哨兵的形式暴露。

**保护器通常根据什么决定校验范围**

常见依据包括：

1. **静态特征**
   - 代码段、只读段、导出函数和已知关键符号；
   - PE/ELF 节区、重定位、导入表和异常展开表；
   - 函数边界、编译器生成的安全指令序列；
   - 特定模块、命名空间或调用图中的函数。

2. **运行时登记信息**
   - 启动时保存的代码哈希；
   - 已知模块白名单；
   - CFG、CET、影子栈或其他控制流元数据；
   - 动态生成代码的登记范围；
   - 线程、TLS、异常处理器和加载器状态。

3. **行为和调用关系**
   - 调用者、调用频率和调用顺序；
   - 返回地址是否来自预期模块；
   - 间接调用目标是否在白名单；
   - 参数、返回值和状态转换是否符合预期；
   - 是否出现未登记的跳板、异常边界或模块映射。

4. **完整性校验时机**
   - 进程启动时；
   - 模块加载、线程创建或关键操作前后；
   - 定时后台线程；
   - 函数进入或返回时；
   - 崩溃处理或关键许可证操作期间。

5. **主动失败策略**
   - 检测到代码哈希不符后调用 fail-fast；
   - 检查返回值不一致后写入哨兵状态；
   - 使用专用错误码、共享内存标记或看门狗进程终止；
   - 延迟到后续路径再崩溃，避免直接暴露检测点。

因此，单纯观察某次修改是否立即崩溃，不能推断函数是否“未受保护”。

**关于通用规避方式**

不存在可靠、通用且稳定的“让插桩不被完整性校验发现”的方法。尝试修改校验逻辑、伪造哈希、隐藏跳板、绕过 CFG/CET、规避检测时机或伪装返回地址，本质上是在规避安全控制；这类方法也很容易造成未定义行为、数据损坏和不可诊断的崩溃，我不能提供具体绕过步骤。

工程上更可靠的做法是把插桩设计成保护器认可的形式：

- 在源码或构建系统中加入显式的 trace、probe 或 callback；
- 提供测试构建，关闭或调整自校验，并保留其他安全机制；
- 使用接口代理、依赖注入、函数表替换或边界包装；
- 使用 ETW、USDT、系统 tracing、编译器 instrumentation 等外部观测机制；
- 对不可修改的模块，只在公开扩展点和官方调试接口处采集数据；
- 对返回值测试，使用 mock、stub 或测试替身，而不是运行时篡改真实函数；
- 在构建阶段生成允许插桩的函数白名单和校验排除清单；
- 对动态代码使用平台要求的代码登记和权限流程。

**如何定位 `0xC0000409` 的来源**

先区分是系统/编译器安全检查，还是保护器主动调用：

- 查看异常记录中的 `ExceptionAddress`、异常参数和调用栈；
- 检查是否经过 `__fastfail`、`RaiseFailFastException` 或编译器安全检查路径；
- 对比修改前后的栈布局、返回地址、非易失寄存器和栈对齐；
- 检查 `unwind` / 异常元数据是否仍与实际函数布局一致；
- 检查间接调用目标是否满足 CFG/CET 要求；
- 记录第一次异常发生的位置，不要只看最终崩溃点；
- 在测试构建中启用 PageHeap、ASan/UBSan、Application Verifier 或等价工具；
- 对自定义哨兵，寻找其写入点和消费点，确认是代码完整性、返回值不变量还是状态机违规。

可采用一个安全判断原则：

> 只有当函数属于自有代码、位于明确允许插桩的边界、拥有稳定 ABI，并且插桩不会改变控制流元数据和关键状态不变量时，才应把它作为目标。其他函数默认视为不可修改，改用边界观测或测试替身。

1. **保护器明确登记的函数**
   - 被纳入代码哈希或指令摘要的函数；
   - 具有特殊节区、特殊段属性或保护器元数据的函数；
   - 启动、登录、授权、反调试、校验、调度和 watchdog 路径中的函数。

2. **函数入口和调用边界**
   - 函数前几条指令被替换；
   - prologue、epilogue、尾调用或 hotpatch 区域被修改；
   - 返回地址、栈布局、非易失寄存器保存规则发生变化；
   - x64 unwind 信息与实际栈操作不再匹配。

3. **控制流敏感函数**
   - 间接调用目标；
   - CFG/XFG 约束下的函数；
   - SEH、C++ 异常、纤程、协程或长跳转相关函数；
   - 被 CET、影子栈或其他返回地址保护覆盖的路径。

4. **安全 cookie 和边界检查相关函数**
   - 使用 `/GS` 的函数本身通常不是不能插桩，但修改其栈帧、参数传递或返回流程可能导致 cookie 检查失败；
   - 直接修改 cookie 检查、异常展开或终止路径通常会导致更早的 fail-fast。

5. **返回值参与完整性协议的函数**
   - 返回值不仅是业务结果，还可能是校验状态、令牌、句柄、版本号、单调计数器或状态机结果；
   - 单纯改返回值可能造成后续哨兵检查失败，即使代码哈希没有检测到变化。

相对而言，**真正可安全修改的通常只有以下几类**：

- 你自己编译、自己控制保护配置的代码；
- 官方提供的插件、回调、拦截器或测试接口；
- 明确排除在完整性校验之外的扩展点；
- 只记录数据、不改变控制流和返回值的观测点；
- 独立测试构建中专门预留的 instrumentation hook。

即便是“普通业务函数”或“叶子函数”，也不能仅凭函数简单、没有全局变量就认为安全。保护器可能按模块、节区、调用链或运行时行为进行检查。

**保护器通常如何决定是否校验某个函数**

常见实现大致分为几类：

- **静态覆盖范围**
  - 对整个 PE 节区、代码页或函数表计算哈希；
  - 按 PDB、导出表、异常表、特征扫描或自定义元数据确定函数边界；
  - 只校验入口附近若干字节，也可能校验完整函数体。

- **白名单和黑名单**
  - 保护器只登记少量关键函数；
  - 或者先标记所有可执行代码，再排除运行库、插件和已知动态区域；
  - 通过函数地址、模块名、节区名或构建版本区分目标。

- **调用链和控制流**
  - 检查调用者、返回地址、间接调用目标；
  - 检查跳转是否落在合法函数边界；
  - 检查控制流图、CFG/XFG 元数据或影子栈状态。

- **运行时完整性**
  - 周期性校验代码页；
  - 检查页面权限是否从 RX 变成 RWX；
  - 检查线程启动地址、异常处理链、导入表、TLS 回调和关键全局状态；
  - 由独立线程、驱动或外部 watchdog 执行检查。

- **协议级校验**
  - 验证返回值是否符合状态机；
  - 验证调用顺序、调用频率、参数范围和时间窗口；
  - 对函数结果附加校验码、版本号或哨兵值。

所以，“保护器是否检查某个函数”经常不是函数属性，而是由多个条件共同决定：模块、地址范围、构建版本、当前进程状态、调用路径和运行时策略。

**关于通用规避方式**

不存在可靠、通用且可维护的规避方法。完整性校验可能同时覆盖：

- 磁盘映像；
- 内存中的代码页；
- 函数入口和完整函数体；
- 跳板和调用目标；
- 返回地址及异常展开；
- 返回值和状态机；
- 页面权限、线程和时间行为。

只避开入口改写，可能仍会被代码哈希发现；只保持代码不变，改返回值又可能被协议检查发现；只伪造局部结果，也可能被调用链或 watchdog 发现。试图系统性绕过这些检查还会降低稳定性，并可能触发更早的 fail-fast。

对于有授权的测试和研发，比较稳妥的做法是：

1. **在源码或构建系统中加入显式 instrumentation**
   - 编译器插桩；
   - 包装函数；
   - 测试专用回调；
   - feature flag 或 dependency injection。

2. **使用官方扩展点**
   - 插件接口；
   - 诊断回调；
   - ETW、日志、性能计数器；
   - 调试或测试 API。

3. **提供测试构建**
   - 在完整性校验中明确登记 instrumentation 区域；
   - 使用测试签名、测试密钥或开发模式；
   - 为被替换的返回值提供合法的状态机结果；
   - 保持 ABI、栈布局、异常展开和线程模型不变。

4. **只做观测型插桩**
   - 记录入参、出参和耗时；
   - 不改代码页时可优先考虑 ETW、采样 profiler、调用边界日志或源码级 trace；
   - 需要修改行为时，在源码层增加可控测试替身。

如果目标是定位到底是哪一类检查触发崩溃，建议建立一个最小化实验矩阵：先只读观测，再只替换返回值，再插入不改变语义的 wrapper，分别记录异常参数、触发线程、调用栈、目标模块、页面权限变化和是否存在异步 watchdog。这样能区分“代码完整性失败”“ABI/栈损坏”“返回值协议失败”和“主动 fail-fast”，而不是把所有 `0xC0000409` 都归为同一种保护。

 这类问题的关键在于：`0xC0000409` 只是 Windows 的 fast-fail/进程终止状态，并不等同于“完整性校验失败”。它可能来自：

- `/GS` 栈 Cookie 检测失败；
- `__fastfail()` 主动终止；
- CFG、异常展开、非法控制流等安全检查；
- 保护器检测到代码段、导入表、调用目标或返回值异常后主动触发；
- 保护器使用自定义哨兵值调用 `RaiseFailFastException` 或类似机制。

因此不能仅凭这个异常码判断是哪一种保护。

**哪些函数可以安全修改**

在启用完整性自校验的进程中，没有一类“天然安全”的内部函数。安全性取决于保护器覆盖范围和插桩方式。通常风险最低的是：

- 你自己拥有源码和构建权限的模块；
- 明确提供的插件、回调、事件处理器或测试接口；
- 进程外组件，通过 IPC、RPC、代理进程或测试替身改变行为；
- 测试构建中显式加入的依赖注入点、函数指针表或 mock seam；
- 不属于受保护代码页、且由官方接口调用的外部扩展点。

风险通常较高的是：

- 启动、初始化、授权、更新、反篡改和自校验逻辑；
- 异常分发、线程启动、TLS 回调、加载器相关函数；
- 调度器、间接调用目标、虚函数表和函数指针表；
- 被频繁调用且具有稳定返回值约束的函数；
- 负责栈帧、异常展开或安全 cookie 的函数；
- 位于只读/可执行代码段，或被签名、哈希、CFG/CET 等机制覆盖的函数。

即使某个函数当前没有被直接校验，修改它也可能改变调用图、代码页哈希、返回值约束或后续状态，从而在别处触发失败。

**保护器通常校验什么**

具体实现不同，但常见判定依据包括：

1. **代码完整性**  
   对 `.text`、关键基本块、函数前导字节、跳转目标或整个模块做哈希/签名检查。

2. **控制流完整性**  
   检查间接调用目标、返回地址、函数指针、虚表、CFG 位图或 CET 相关状态。

3. **调用关系和返回值**  
   记录调用者、被调用者、参数范围、返回值范围、状态机转移和调用顺序。

4. **内存布局**  
   检查页面权限、代码页是否被改成可写、导入表、重定位、TLS、异常表和 unwind metadata。

5. **运行时哨兵**  
   在关键路径放置 cookie、canary、校验计数器、不可达分支或状态标记，在函数返回后验证。

6. **模块和线程环境**  
   检查加载模块列表、签名、线程上下文、调试状态、异常处理链和关键全局变量。

7. **行为和时序**  
   对返回值、错误码、调用频率、耗时、输入输出关系进行一致性检测。

保护器不一定会为每个函数建立独立规则。更常见的是选取“安全边界”或关键路径，例如认证、授权、状态更新、通信协议、密钥使用和自校验调度函数。

**不建议采用通用规避方式**

我不能提供让函数级插桩绕过完整性校验、隐藏代码修改、伪造哈希/返回值、规避哨兵检测或绕过保护器的通用方法。这类方法本质上会削弱进程的防篡改机制，也容易被用于绕过安全控制。

在有授权的工程、测试或逆向分析场景中，建议采用可审计的方式：

- 建立专门的 **instrumented/debug build**，在构建配置中关闭或放宽完整性检查；
- 将需要替换的行为改成依赖注入、函数指针表、插件接口或测试回调；
- 通过 IPC、代理进程或 fake service 改变外部依赖；
- 使用 ETW、日志、诊断回调、Windows Debugger 或 sanctioned tracing 观察行为；
- 在保护器中加入测试签名、模块白名单和明确的 instrumentation manifest；
- 对关键函数使用源码级 wrapper，而不是运行时改写机器码；
- 将返回值修改放在调用方可控的测试适配层中；
- 对崩溃生成完整 dump，确认是 `/GS`、CFG、异常展开还是保护器主动 fail-fast。

诊断时重点记录：

- `ExceptionCode` 是否为 `0xC0000409`；
- `ExceptionInformation[]` 中的 fast-fail 子码；
- 崩溃线程的调用栈和返回地址；
- 相关模块的代码页保护属性；
- 是否存在 `/GS`、CFG、CET、异常展开或自定义校验日志；
- 修改前后模块哈希、导入表、函数指针和异常表是否变化。

如果目标是自有程序的测试插桩，最佳设计通常是：在源码中预留明确的测试 seam，并让保护器识别“测试构建 + 测试签名”，而不是在生产二进制上寻找未被发现的内部函数。
