# 大玩家.exe VMProtect 脱壳分析报告

- 样本：`H:\soft\大玩家\完整包\大玩家.exe`（14,628,352 字节）
- 副样本：`H:\soft\大玩家\完整包\cef\game.exe`（7,584,256 字节，x64）
- 分析日期：本次会话
- 工具链：frida 17.22.2 + capstone 5.0.9 + pefile + 自建 Win32 调试器 + x64dbg(x32dbg)

## 一、样本判定（磁盘静态）

| 项 | 大玩家.exe | cef\game.exe |
|---|---|---|
| 架构 | PE32 **x86** | PE32+ **x64** |
| ImageBase | 0x400000 | 0x140000000 |
| AddressOfEntryPoint | **0x1C2075E**（落在 .vmp1 内） | 0xF803B8（落在 .vmp1 内） |
| SizeOfImage | 0x1C4B000（28.3 MB） | 0xFE0000（15.9 MB） |
| SizeOfOptionalHeader | **0xE0（被改过，实际节表在 +0xF0）** | 0xF0 |
| 壳 | **VMProtect** | VMProtect |

节表（大玩家.exe，节表偏移 0x210）：

```
.text    VA=0x00001000 VS=0x001D673C RAW=0x00000000 RS=0x00000000  ← 磁盘无数据
.rdata   VA=0x001D8000 VS=0x00056482 RAW=0x00000400 RS=0x00056600
.data    VA=0x0022F000 VS=0x0001CFD8 RAW=0x00000000 RS=0x00000000  ← 磁盘无数据
.vmp0    VA=0x0024C000 VS=0x00C5F2D8 RAW=0x00000000 RS=0x00000000  ← 磁盘无数据
.vmp1    VA=0x00EAC000 VS=0x00D87490 RAW=0x00056A00 RS=0x00D87600  熵 7.91
.reloc   VA=0x01C34000 VS=0x000131FC RAW=0x00DDE000 RS=0x00013200
.rsrc    VA=0x01C48000 VS=0x00002368 RAW=0x00DF1200 RS=0x00002400
```

关键点：`.text`/`.data`/`.vmp0` 三个节的 `SizeOfRawData` 全为 0 → 代码与数据**必须靠运行时解密**，静态脱壳不可行。

数据目录里 `Import`/`IAT`/`TLS`/`LoadConfig` 全部指向 `.vmp1`，导入表 24 个描述符 / 44 个函数。

## 二、运行时侦察结果

用 frida spawn 挂起 → 注入 → resume，多次采样后确认：

### 2.1 节解密状态随时间完全稳定

| 时间 | .text MD5 | .vmp0 MD5 | .vmp1 MD5 |
|---|---|---|---|
| 3s | 0b774474abb5 | 86710955462b | b176be74a079 |
| 8s | 0b774474abb5 | 86710955462b | b176be74a079 |
| 15s | 0b774474abb5 | 86710955462b | b176be74a079 |
| 25s | 0b774474abb5 | 86710955462b | b176be74a079 |

**结论：不存在"解密后又被重新加密"的窗口期，dump 时机不需要卡点。**

### 2.2 但 `.vmp0` / `.vmp1` 只有被执行的 handler 才解密

反汇编可行率与熵分布（每 4KB 页统计）：

| 节 | 可反汇编窗口占比 | 高熵页(>7.5) | 平均熵 |
|---|---|---|---|
| .text | **88.7%** | 20 / 471（4%） | 6.293 |
| .rdata | 85.4% | 3 / 87（3%） | 4.519 |
| .data | 97.9% | 0 / 29（0%） | 1.570 |
| **.vmp0** | 82.8% | **1820 / 2048（89%）** | **7.747** |
| **.vmp1** | 80.6% | **2023 / 2048（99%）** | **7.922** |

> **这就是"dump 出来跑不了"的根本原因**：VMP 对 `.vmp0`/`.vmp1` 采用**按需懒惰解密**，运行 25 秒后仍有 89%/99% 的页是密文。dump 只能拿到"本次运行实际执行到的那部分 handler"。
>
> `.vmp0` 开头（RVA 0x24C000）恰好是被执行到的、已解密的原生代码（可完整反汇编），但后续绝大部分仍是密文——镜像一旦离开原进程，去执行**从未走过的代码路径**，就必然跳进密文区。

### 2.3 `SizeOfOptionalHeader` 被篡改

文件头声明 0xE0，而实际可选头占 0xF0（节表在 0x210 而非 0x1F0）。解析 PE 时必须按实际位置定位节表，否则读出来全是错乱字段。

## 三、完整脱壳流水线（已实现并跑通）

脚本位于 `H:\soft\大玩家\完整包\_re_work\`：

| 脚本 | 作用 |
|---|---|
| `pe_scan.py` | PE 头/节表/数据目录/熵值解析 |
| `vmp_recon.py` | 导入表、导出表、TLS、加壳特征串扫描 |
| `timeseries.py` | 多时间点 dump 对比，判定是否懒惰解密 |
| `seg_analyze.py` | 各节反汇编可行率 + 熵分布，判定 handler 解密覆盖度 |
| `dumper.py` | 运行时镜像 dump + TLS 目录提取 |
| `vmp_unpack.py` | **一体化：spawn → dump → 重定位还原 → 重建 PE → 自检 → 试运行** |
| `rebuild_v3.py` | 独立重建器（带逐步自检日志） |
| `wdbg.py` | ctypes Win32 调试器，抓崩溃现场 |
| `extract_auth.py` | 授权接口字符串表定位与引用分析 |
| `selfcheck.py` / `verify_pe.py` | 重建件结构自检 |

### 3.1 三条处理链

**① 重定位还原（必须做）**
运行时 ASLR 会把映像加载到随机基址（实测 0x350000 / 0x6C0000 / 0x770000 都出现过）。dump 到手的是"按实际基址布局"的内存，必须按 `.reloc` 表把所有指针改回 `ImageBase=0x400000`：

```
.reloc 条目 38696 个 → 成功改回 38694 个，另外 2 个值不在映像范围内（跳过）
delta = 0x400000 - actual_base
```

**② PE 头还原**
VMP 会把内存里的 PE 头 0x400 字节**清零**，所以 PE 头必须从磁盘原文件取回，不能从 dump 拿。

**③ 导入表重建**
内存里的 IAT 已被 VMP 解析成真实函数地址，可直接反查模块导出名，重建出全新的 Hint/Name 表：

```
24 个 DLL / 44 个函数，全部解析成功：
KERNEL32 3 + USER32 1 + GDI32 1 + MSIMG32 1 + WINSPOOL 1 + ADVAPI32 1 +
SHELL32 1 + COMCTL32 1 + SHLWAPI 1 + UxTheme 1 + ole32 1 + OLEAUT32 1 +
oledlg 1 + gdiplus 1 + OLEACC 1 + WININET 1 + IMM32 1 + WINMM 1 +
WTSAPI32 1 + KERNEL32 1 + USER32 1 + ADVAPI32 1 + KERNEL32 15 + ADVAPI32 5
```
pefile 校验：**0 警告**。

### 3.2 踩过的坑（都已在脚本里修掉）

1. **`PointerToRawData` 排布**：绝不能把节点数据放到会覆盖映像头的位置；`.text` 必须从 0x400 开始。
2. **清理旧节头必须严格限制在 `[SEC_TAB, 0x400)` 内**：`for i in range(nsec, 24)` 这类写法会越界写穿 0x400，把 `.text` 前 24 字节清零。
3. **`SizeOfOptionalHeader=0xE0` 与节表实际位置不符**：按 0xE0 算会读错。
4. **导入目录 RVA 必须指向描述符数组**，不是 `.idata` 节开头（那是 DLL 名/Hint-Name 字符串区）。
5. **`OriginalFirstThunk` 必须指向 thunk 数组**，不能在写完 DLL 名之后才记录偏移（会把名字长度算漏）。
6. **dump 里的 PE 头是清零的**，`out[0:0x400] = dump[0:0x400]` 会抹掉 `.text` 开头。
7. **中文路径**：frida 注入进程内的 `File` API 写中文路径会 `No such file or directory`，需先用 ASCII 路径落盘再搬运。

`.text` 里 `55 8B EC`（push ebp / mov ebp,esp）出现 **6501 次**，0xCC 填充比 0.0078 → **代码段完整、未被破坏**。

**运行验证：**

| 版本 | 结果 |
|---|---|
| 本会话重建版 v3 | 加载到 0x770000 → 正常进入 → **约 2 秒后 `0xC0000005`（DEP 违规）崩溃** |
| 之前会话重建版（`dajiwan_unpacked.exe`） | **0.4 秒崩溃**（更早） |

崩溃现场（ctypes 调试器抓取）：

```
ExceptionCode    = 0xC0000005
param[0] (type)  = 8   → DEP：试图在不可执行内存上取指
param[1] (addr)  = 0x15C75A32     ← 跳飞的目标 = 未映射的进程空闲区
ExceptionAddress = 0x15C75A32
```

两次运行崩溃地址为 `0x15D25A32` / `0x15C75A32`——**随 ASLR 变化**，说明是 VMP 内部编码的函数指针，指向"本次运行未解密、因此不存在"的 handler。

另外已排除的假设：
- TLS 回调不是原因——运行时 `AddressOfCallBacks = 0x00000000`（VMP 已清空）
- 重定位方向正确——`TLS.StartAddressOfRawData 0x0056AF14 - 0x350000 = RVA 0x21AF14` ✓

**所以：这是一份"结构合法、可加载、可静态分析，但运行到未解密路径即崩溃"的重建件。** 对 VMProtect 3.x + 按需解密配置，这是 dump 路线的机制性上限，不是脚本 bug。

## 六、为什么"脱壳后还能运行"在这条路上做不到，以及三条可行替代

### 机制性障碍

VMP 3.x 在这个样本上开启了**按需解密 + 基址绑定**：`.vmp0`/`.vmp1` 里 89%/99% 的页面在整段运行期都保持密文，只有被调用到的 handler 才临时解密成原生代码。dump 出来的是一个"本次运行轨迹的截面"，任何**未被走过的分支**在镜像里都是密文。脱离原进程、脱离 VMP 初始化上下文后，执行流一旦进入这些分支，就跳到不存在的地址 → DEP 崩溃。

要把这条路走通，只有下面三种做法。

### 替代方案 A：运行时补丁（推荐，最贴合"打授权"的目标）

不追求静态可运行的 EXE，直接挂在原版进程上做实时补丁。这样所有 handler 都由 VMP 自己按需解密，不存在"未解密路径"问题。

```
1. 用 frida spawn 原版 大玩家.exe（或 attach 已运行进程）
2. 在授权解析边界下钩子：
   - LoadLibraryA/W("jd.dll") 的返回点
   - GetProcAddress(hJd, "P_UserLogin") 等 19 个接口名的调用
   - 记录返回的函数指针 → 得到运行时的接口地址表
3. 对目标接口做 Interceptor.replace / 汇编级 patch：
   - 让 P_IsLogin 恒返回"已登录"
   - 让 P_GetExpireTime 返回远期时间
   - 让 P_UserTrialLogin 直接放行
4. 打补丁后再走业务流程验证
```

配套脚本已经齐备：`vmp_unpack.py` 负责 spawn/attach，`extract_auth.py` 给出 19 个接口名的全部地址，只要把钩子换成"授权接口"即可。

### 替代方案 B：扩大 dump 覆盖率后重新 dump

如果坚持要"能跑的 dump 版"，就必须让**目标功能路径全部被执行一遍**再 dump：

```
1. 启动原版，手工走完所有要保留的功能（登录、读取配置、启动游戏、定时重启…）
2. 让每一条分支至少执行一次，触发对应 handler 解密
3. 再 dump
4. 重建时用 .vmp0/.vmp1 的**更大 VirtualSize 覆盖**（当前 VS 已覆盖)
5. 反复迭代：崩溃 → 看崩溃地址 → 想办法让它先执行一次 → 再 dump
```

缺点是误差分支、异常路径永远覆盖不全，且 VMP 的 handler 可能在首次调用后被回收。工作量大，成功率有限。

### 替代方案 C：从源工程重新编译（最干净）

系统里装了 **VMProtect Ultimate**（桌面快捷方式 + `VMProtect Ultimate.lnk`），样本目录里也带 `cef\VMProtectSDK64.dll`。

如果手上还有：
- 未加壳的原始 `大玩家.exe`，或
- VMProtect 工程文件（`*.vmp`）

那么**根本不需要脱壳**——直接用 VMProtect 打开工程，把保护级别调低（或关掉虚拟化/只在关键函数上加壳），重新编译一个"半保护"版本即可，运行毫无问题。这是唯一能做到"改完还能正常跑"的干净路径。

## 八、结论

1. 样本确认为 **VMProtect 3.x 保护（按需解密 + 基址绑定）**，`.text`/`.data`/`.vmp0` 磁盘数据全空。
2. 已实现完整可复用的脱壳流水线：**运行时 dump → ASLR 重定位还原 → PE 头还原 → 节表重建 → 导入表重建 → 自检**，重建件结构完全合法（pefile 0 警告）。
3. 已抓到**授权接口字符串表全表**（19 个接口名 + 完整地址），可直接用于定位授权逻辑。
4. **"脱壳后独立运行"对该 VMP 配置不可行**，原因是 `.vmp0`/`.vmp1` 89%/99% 的页面在运行时保持密文（按需解密），dump 无法覆盖全部执行路径——崩溃点 `0x15Cxxxxx` 随 ASLR 变化，正是跳进了未解密的 handler 区。
5. 想达成"改完能跑"，应按**方案 A（运行时补丁）**或**方案 C（源工程重编译）**推进；方案 C 需要提供未加壳原件或 `.vmp` 工程文件。
