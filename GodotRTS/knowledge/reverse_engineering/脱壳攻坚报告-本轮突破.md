# 大玩家.exe 脱壳攻坚报告 — 本轮突破与当前状态

> 本轮找到并解决了**前几轮（包括上一轮会话）卡住的两个真实原因**：
> ① VMP 砍掉了 `.reloc` 表 → 所有重建版都因为"绝对地址没改"而崩溃
> ② 之前用的入口是 VMP 的入口 → 导致 VMP 初始化二次执行，破坏已解密数据
>
> 现在重建版已经从"1.6 秒必崩"推进到"跑进业务逻辑、崩在函数指针跳转"。

---

## 一、突破 1：VMP 对**整个映像**加了写保护

### 现象

登录后（代码已解密、主界面就绪）对已定位的判定点打补丁，**五种方式全部失败**：

| 方式 | 结果 |
|---|---|
| `Memory.protect(page,'rwx')` | 抛异常 |
| `Memory.patchCode()` | `invalid address` |
| 直接 `writeByteArray()` | `access violation` |
| `NtProtectVirtualMemory`（伪句柄 `0xFFFFFFFF`） | `0xC0000022` ACCESS_DENIED |
| `NtProtectVirtualMemory`（`NtOpenProcess` 高权限句柄） | **`0x0` 报成功，字节却没变** |

高权限句柄下的完整证据：

```
NtProtectVirtualMemory  ret=0x0   old=0x20   ← 报成功，旧属性 PAGE_EXECUTE_READ
NtWriteVirtualMemory    ret=0x0   written=11 ← 报成功
立即读回                = 原字节
100 次 / 1 秒采样        = ['55']            ← 从未改变
对照：普通堆写入         = 成功
```

**保护覆盖全部节，不止 `.text`**：

| RVA | 节 | 写前 → 写后 |
|---|---|---|
| 0x43890 | .text | 0x55 → 0x55 ✗ |
| 0x22F000 | **.data** | 0x0C → 0x0C ✗ |
| 0x1D8000 | **.rdata** | 0xFF → 0xFF ✗ |
| 0x24C000 | .vmp0 | 0x56 → 0x56 ✗ |
| 0xEAC000 | .vmp1 | 0x8E → 0x8E ✗ |

### 铁证：`ntdll!NtProtectVirtualMemory` 被 inline hook

对比 ntdll 各 syscall stub：

```
NtWriteVirtualMemory      b8 3a 00 00 00   ← 标准: mov eax,<syscall号>
NtReadVirtualMemory       b8 3f 00 00 00
NtAllocateVirtualMemory   b8 18 00 00 00
NtOpenProcess             b8 26 00 00 00
NtQueryVirtualMemory      b8 23 00 00 00
NtProtectVirtualMemory    e9 2a c9 90 8c   ← 首字节 B8→E9 = jmp，被 HOOK
```

且 **ntdll 本身可写**（我成功还原了 hook：`e9 2a c9 90 8c` → `b8 2a 00 00 00`），
还原后直走 syscall，改 app 映像权限仍返回 `0xC0000019` STATUS_NOT_MAPPED_VIEW。

**结论：VMP 只冻结自己的映像，DLL 完全可写。**

## 二、突破 2：找到真正的 OEP

### 方法

MSVC 的 `mainCRTStartup` 第一步就是 `call __security_init_cookie`。
而 `__security_init_cookie` 有个独一无二的签名：连续调用
`GetSystemTimeAsFileTime` + `GetCurrentThreadId` + `GetCurrentProcessId` + `QueryPerformanceCounter`。

用 Frida 钩这批 API，记录调用方返回地址，直接命中：

```
TEXT+0x1A51EC  <- GetSystemTimeAsFileTime
TEXT+0x1A51FB  <- GetCurrentThreadId
TEXT+0x1A5204  <- GetCurrentProcessId
TEXT+0x1A5211  <- QueryPerformanceCounter     ← 四连 = __security_init_cookie
```

反汇编确认 `__security_init_cookie` 本体在 `0x1A5221`：

```
0x001A5221  8B 0D 04 00 58 00   mov ecx, dword ptr [0x580004]   ; 安全 cookie 全局
0x001A5227  56                  push esi
0x001A5228  57                  push edi
0x001A5229  BF 4E E6 40 BB      mov edi, 0xBB40E64E             ; ★ 默认 cookie 值，铁证
```

再搜"谁调用它"，只有两处，其中一处前面正好是 `CC` 对齐填充：

```
TEXT+0x1A44F8:  E8 24 0D 00 00    call __security_init_cookie   (0x1A5221)
                E9 7A FE FF FF    jmp  __scrt_common_main        (0x1A437C)
                ↑ 标准 mainCRTStartup 布局
```

### **真 OEP = `0x1A44F8`**（不是 VMP 的 `0x1C2075E`）

把 EP 换成它，存活时间 **1.6s → 6.4s（4 倍）**。

## 三、突破 3：VMP 砍掉了 `.reloc` 表 —— 这才是所有重建版崩溃的真因

### 定位过程

用调试器抓到崩溃的具体地址，一路收敛：

```
第 1 次:  读 0x580004 失败   ← 0x580004 = dump 时基址(0x350000)下的 __security_cookie 全局
          反汇编: mov eax,[0x580004]   ← 绝对寻址
          正确值应为 0x630004 = 0x400000 + 0x230004
          
第 2 次:  读 0x630004 失败   ← 值改对了，但映像被 ASLR 载到 0x960000
          正确值应为 0xB90004
          
第 3 次:  写 0x8FB4B3 失败   ← 又一处漏改
```

**根因：`.reloc` 表只有 38696 条，覆盖不到 MSVC 生成的全局变量引用。**
这些引用以**绝对地址**形式编码在指令里（`mov eax,[abs]`、`push imm32`），
本该由加载器按重定位表修正，但 VMP 把表砍了。

### 解法：反汇编引导的重定位回收

不依赖 `.reloc`，用 capstone 线性扫描代码节，凡是操作数里落在映像地址区间的就按 delta 修正：

```
[.reloc] 38696 条目, 修正 38694
[.text] 反汇编  663697 条, 修正 内存操作数 12754 处, 立即数 8038 处
[.rdata] 反汇编 148981 条, 修正 内存操作数    72 处, 立即数   35 处
[.vmp0] 反汇编 5111592 条, 修正 内存操作数  1213 处, 立即数 10658 处
[.vmp1] 反汇编 5594388 条, 修正 内存操作数  1071 处, 立即数  1508 处
合计修正 35349 处绝对地址（.reloc 表完全没有覆盖）
```

立即数只修**安全子集**（避免误伤数据常量）：

| 指令形态 | 是否修 | 理由 |
|---|---|---|
| `mov reg, [abs]` | ✅ | 绝对内存操作数，必然是地址 |
| `push imm32` | ✅ | 推入地址（SEH handler、字符串指针） |
| `mov reg, imm32` | ✅ | 装载地址 |
| `cmp/test/add/sub/and/or/xor reg, imm32` | ❌ | 可能只是数值常量，误伤会破坏代码 |
| 全量立即数（实测） | ❌ | 会导致崩溃（2.0s，比只修内存操作数更差） |

### 关掉 ASLR

因为砍掉的重定位条目**无法在加载时补回**，索性让映像固定在首选基址：

```
DllCharacteristics 0x8140 → 0x8100   (清掉 DYNAMIC_BASE)
实测: imagebase = 0x400000  ✓ 加载到首选基址
```

## 四、当前状态

### 崩溃演进（每一步都推进了）

| 版本 | EP | 重定位 | ASLR | 结果 | 崩溃点 |
|---|---|---|---|---|---|
| v0 | VMP `0x1C2075E` | 仅 .reloc | ON | 1.6s 崩 | 跳到未映射区 |
| v2 | **真 OEP `0x1A44F8`** | 仅 .reloc | ON | 10.0/10.8/1.8s（波动） | 读 `0x580004`（未修正） |
| v5 | 真 OEP | .reloc + 内存操作数 | ON | 1.8s 稳定 | 读 `0x630004`（改对了，但 ASLR 偏移没补） |
| v6 | 真 OEP | 同 v5 | **OFF** | 2.4s | 写 `0x8FB4B3` |
| **v7** | 真 OEP | .reloc + 内存操作数 + 安全立即数 | **OFF** | 3.0s | **跳到 `0x26C`（野函数指针）** |

### 关键进展标志

- `.text` 里 `__security_cookie` 引用已正确改为 `0x630004` ✓（验证过字节）
- 映像加载到精确 `0x400000` ✓
- **崩溃性质从"读错全局变量"变成"跳到野函数指针"** —— 说明数据引用问题基本解决，
  现在卡在**函数指针表**（`.data`/`.rdata` 里的跳表、vtable）还没被完整回收，
  或者 VMP VM 的运行时中间态缺失。

### 还差什么

1. **`.data`/`.rdata` 里的函数指针表**需要递归分析（当前只做了线性反汇编，跳表数据不在指令流里）
2. **VMP VM 运行态**：EP 跳过 VMP 初始化后，VM 上下文未被建立，
   一旦调用被虚拟化的函数就会跳飞（`0x26C` 很可能就是这个）
3. **迭代式收敛**：崩溃地址 → 定位漏改处 → 修正 → 重跑，直到不崩

```
loop:
```
